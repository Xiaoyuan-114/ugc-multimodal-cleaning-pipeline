# 清洗流水线方法论

面向「几千条记录 + 几万张图」的 UGC 数据集。目标不是“尽量多删”，而是**每条决定都可审计、数量守恒、原始数据零改动**。

## 七步架构

```
step1 输入盘点   → 扫描所有表/工作表/图片，产出清单 + 运行前 manifest（路径→size/mtime）
step2 图片指纹   → SHA-256 + 解码状态 + 全黑/全白比例 + 灰度标准差（多线程，JSONL 可续跑）
step3 记录归并   → 按平台主键合并，字段错位核实，产出规范记录 + 原始行映射
step4 校准批     → 抽 100–150 条 + 定向探针，跑完整判定，人工核对口径（关键闸门）
step5 全量判定   → 逐条追加 JSONL，断点续跑；预过滤分支跳过注定被排除的记录
step6 出表归档   → 去重 + 复制图片 + 审计文件 + 守恒校验
step7 终局改名   → 校验全过后才把临时目录改名为正式目录
step8 交付说明   → 在正式目录内写交付说明（文件清单/字段/原因码/已知情况/不包含范围）
```

## 关键设计决策

### 1. 两级判定，图片级与记录级用不同规则

- **图片级**：判断“这张图本身是不是纯推广物料”（价目表/二维码/海报/营销模板）。取景良好的风景照、人物照、样片**一律不算广告图**——用“图中是否有真实景观内容”一票否决。
- **记录级**：判断“这条内容整体上是不是在招揽生意”。**不要**用“配图里有没有风景”当否决条件——否则凡是配了风景照的旅拍/妆造/民宿招揽帖永远排不掉。
  - 正确做法：让模型输出一个主旨字段（如 `record_is_travel_experience`），问“帖子主旨是记录游览，还是招揽生意”。
  - 游记里顺带提到“这家店拍得不错” → 主旨仍是游览 → 保留。
  - 字段缺失/不确定 → 一律视为“游览”（保守保留）。

### 2. 确定性守卫必须与模型证据隔离

范围守卫（“某个来源关键词召回的内容只保留本地”）**只能扫描记录自身的可核查文本**（标题/正文/转发/关键词）。**绝不要把模型返回的证据字段纳入扫描**——模型的说明里常出现“非本地”“不含本地内容”这类反向表述，会把否定句误当成肯定证据，导致守卫永远不触发。

### 3. 守卫 vs 模型的分工要看“词是否该地独有”

- **通用词**（全国多地同名）：命中异地内容比例高 → 加确定性守卫，只保留正文含本地独有词（或挂有其他本地关键词）的记录，其余直接判 `R001` 且**不调模型**（省钱省时，图片按 `inherited_from_record` 归档）。
- **本地真实景点名但各地同名**：**不能加守卫**——本地的照片可能不带地名，加守卫会误杀。只能靠模型读正文里的城市名判断。
- 盘点方法：算每个搜索关键词的“正文含异地城市名比例”，比例高的才考虑加守卫。某项目实测：一个通用地名关键词召回的记录中约 78% 是异地内容，而具体景点名基本干净。

### 4. 校准批要加定向探针

除了按类别分层抽样，额外加针对性的探针组（如“通用词范围”“服务招揽类”），每组 10–16 条。否则随机抽样根本抽不到你要验证的边界情形。

### 5. 守恒校验（最重要）

出表后必须验算，任何一条不成立说明逻辑有洞：

```
规范UGC数 = 可用 + 广告排除 + 不可用排除
原始候选图片数 = 保留 + 同UGC内重复副本 + 广告排除 + 不可用
原始表格行数 = 表格产生的规范UGC数 + 被合并行数
```

配套：原始数据 size/mtime 前后一致；每个候选图片都有状态；保留记录都有文件夹；`image_files` 路径真实存在（无图必须为 `[]`）；抽样比对复制后文件的 SHA-256。

### 6. 先空跑再实跑

出表脚本加 `--no-copy` 开关，先只算表不复制图片，验证逻辑和校验能否全过，再跑真实的十几 GB 复制。

### 7. 广告规则：条件二要问“主旨”

旧规则“不包含真实游览/空间体验/景观环境/地方文化内容”会把配风景照的旅拍/妆造/民宿招揽帖全部漏掉。改写为：
- 条件一：有明确推广证据（联系方式、二维码、购买链接、价格促销、招募、预约接单、私信引流、营销模板）。
- 条件二：**招揽是这条内容的主旨**（`record_is_travel_experience = false`）。
- 两个条件缺一 → 不判广告；字段缺失 → 保守保留。

## 成本与性能（参考）

- 图片按尺寸归一化计费时，每张图的 input token 通常有上限；具体取决于服务商。
- 大多数视觉模型默认开启 thinking/reasoning，若按输出计费会显著抬高成本；批量任务应显式关闭或降到最低档。
- 缓存命中率取决于提示词前缀复用；同一批提示词重跑会明显便宜，首次全量不要指望高命中。
- 峰谷价差可能达到 2 倍：大批量任务排到夜间/周末。
- 先算再做：从校准批的 token 用量外推全量（`每次请求平均 token × 预计请求数`）。
- 真正的约束往往不是费用，而是时间与上传带宽（几万张图需要预压）。

## 输出结构（可审计）

```
输出目录/
├── 可用UGC.csv / .jsonl          # 最终可用记录
├── 清洗明细.csv                   # 全部规范记录，含保留与排除
├── 排除记录.csv                   # 整条 UGC 与单张图片的排除决定 + 证据 + reason_scope
├── 重复映射.csv                   # 完全重复关系（UGC 内 / 跨 UGC）
├── 清洗汇总.csv                   # 分平台统计 + 主原因数量与比例
├── 原始记录映射.csv               # 每条原始表格行的动作
├── 图片明细.csv                   # 每张候选图片的全部状态与程序化检测值
├── 输入文件清单.csv               # 所有扫描项 + 跳过原因 + 运行前后 size/mtime
├── 运行信息.json                  # 模型/参数/阈值/口径/校验结果
├── 交付说明.md                    # 面向接收方
└── images/<平台>/<编码>/
```

## 交付说明（交付给他人时必做）

光有数据一定会被反复追问。在正式目录里放一份 `交付说明.md`，固定写这十节：

1. 一句话说明 + 原始数据未改动的结论
2. 文件清单表（每个文件“装什么 / 什么时候用”）
3. 关键数字与守恒等式（写出验算式子，不只是结果）
4. 字段说明：主键、原始字段 vs 清洗字段、多值字段是 JSON 数组的提醒、CSV BOM 与图片相对路径约定
5. 原因码字典（完整列出 A/R/T/F/D 的含义与作用层级）
6. 判定规则要点（广告口径、保守原则、地点判定只看明确证据、范围守卫）
7. 已知情况与使用提醒：哪些 flag 从未触发及原因、汇总表哪些列按设计为空、口径选择、原始表格错位纠正、未纳入处理的大文件
8. 明确列出不包含的内容（评分、空间特征、建模、锚定），划清边界
9. 复现与验收：run_id / 规则版本 / 代码版本 / 模型 / 成本 / 校验通过数
10. 交接确认清单（可勾选）

一个容易被忽略的点：**把“采集关键词”和“作者正文”分开**。搜索关键词是采集元数据，若把它和正文混在一起统计“提及率/可锚定率”会严重虚高。交付说明里要写清用哪个口径。

## 环境与复现（Windows 实测）

- 部分 Windows 便携版 Git Bash 缺 coreutils：`ls`/`head`/`tail`/`rm` 可能不可用。所有文件操作建议直接用 Python。
- **不要把中文长文本塞进 `bash -c "python -c '...'"`**：反引号和 `$` 会被 shell 当命令替换，写入内容被静默截断且不报错。中文长文本用编辑器或 Write 工具直接写文件。
- 后台任务把输出重定向到日志文件，再用 Read 读，不要依赖 stdout 回显。
- 深度校验类脚本先做 `--no-copy` 空跑验证逻辑，再跑真实全量。

## 铁律

1. 原始数据**只读**：不修改、不移动、不重命名、不删除；复制图片必须字节原样，复制后验 SHA-256。
2. 保守优先：判断不明确一律保留，只设 flag。排除只用于高置信度情形。
3. 多值字段统一写 JSON 数组字符串，不用逗号拼接。
4. 每条排除决定都必须有**唯一主原因** + 可核查的证据（证据类型和位置，不能只写“模型认为是广告”）。
5. 校验不过不改名，不声称完成。
