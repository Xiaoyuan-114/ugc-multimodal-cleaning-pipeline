# 刺激材料与交付打包方法论

上游是「已清洗完成的 UGC 数据集（主表 + 图片目录）」，下游是「另一个 agent / 另一个人在另一种操作系统上按提示词批量调多模态模型」。
本流水线负责中间这一段：把数据集变成机器可直接消费的刺激材料与请求清单，并留下可审计的证据链。

## 8 步

```
y1 样本与文本     → 稳定排序编号 → 样本清单.csv + stimuli/text/{NNNN}.txt
y2 图片重编码     → 统一 长边/质量/剥离 EXIF → stimuli/images/{platform}/{source_id}/*.jpg（多进程 + 断点续跑）
y3 请求清单       → requests.jsonl：每行一个样本的材料清单（相对 POSIX 路径）
y4 痕迹与泄漏扫描 → 扫描平台痕迹 / 采集关键词泄漏；顺带做“文本=字段拼接”逐字节一致性校验
y5 自检 + 台账    → 数量守恒、路径可解析、体积/尺寸上限、SHA-256 抽查 → 自检报告.md + 材料台账.csv
y6 打包           → zip：图片 STORED、文本 DEFLATED；顶层目录改名；抽样 CRC 校验
y7/y8 复制校验    → 逐文件 size 比对补齐 + 全量 SHA-256（跨目录搬运大目录时用）
y9 成本估算       → 按材料台账实际尺寸估算 token 与费用
y10 分卷          → 大 zip 分卷 + 拼接哈希
```

## 关键设计决策（踩过坑的，直接照做）

### 样本单位与编号

- **1 条可用记录 = 1 个样本**。定下后写进提示词与 handoff，**编号一旦对外不可变**。
- 编号：4 位补零 `0001–NNNN`，排序键用 `(platform, record_id)`（确定性、可复现）。
- 图片数**不设上限**，全部给；不要为了省 token 抽样——会引入选择偏差。

### 平台信息必须隔离

- 平台名、昵称、等级、IP 归属、采集关键词（`source_keywords`）**都不喂给模型**。
- 做法不是“小心别带上”，而是**请求清单里根本不放这些字段**（结构上不可能误喂）。
- 采集关键词本身可能是地标名，等于泄题；它绝不能混进正文。自检里要专门查这条。
- 平台字段只留在分析用的 `样本清单.csv` 里。

### 图片重编码

- 面向模型的硬限制通常有“内嵌单文件 ≤ 7 MB”，统一重编码最稳妥：**长边 ≤ 1568、JPEG q90、optimize=True、转 RGB、剥离 EXIF**。
- **原图绝不覆盖**，输出到新目录（原始数据只读是硬规则）。
- 多进程 + JSONL 日志**断点续跑**；重跑时**后出现的日志记录覆盖先出现的**（否则失败的旧记录会污染统计）。
- 记录每张图的 sha256 / 尺寸 / 体积 / 是否缩放 → `材料台账.csv`。

### 提示词改动最小化

- 把提示词当**评分规格**看待：**投喂机制可以改，评分口径不能改**。
- 从“聊天界面拖附件”改成“API 一请求一样本”属于机制适配（数组→单对象、删掉靠附件名提 sample_id 的段落）。
- 若必须触碰评分口径，**只能改一处**，并留一个**天然单点对照**做回归测试（例如“样本 X 是唯一的纯文本样本，预期只有它变”）。
- 产出 `提示词_改动对照.md`：逐条列改动 + 明确列出“逐字保留、不许动”的段落。

### 口径争议的量化打法

- 争议不要靠辩论：**先用词表把样本分层量化**（含特征词 / 只下判断 / 无信息），再决定口径。
- 宁可撤回自己的错误结论，也不要让它进交付文档。

## 跨平台交付（Windows 生成 → macOS 使用）

handoff 里必须逐项写清，这 6 条最容易出事：

| 项 | 做法 |
|---|---|
| 编码 | **CSV = UTF-8 with BOM**（收方读时 `utf-8-sig`，否则首列名多 `\ufeff`）；jsonl/txt = UTF-8 无 BOM |
| 换行 | txt/jsonl 用 LF；CSV 用 CRLF（别统一转 LF，会坑 Excel） |
| 文件名归一化 | macOS HFS+/APFS 存 **NFD**，CSV 里读到的中文名是 **NFC**，`==` 会莫名 False → 比对前 `unicodedata.normalize("NFC", name)` |
| 路径分隔符 | 清单里全部写 **POSIX `/`**，收方直接 `os.path.join(ROOT, rel)`；**不要**用 `os.sep` 再替换 |
| zip 顶层目录 | zip 内顶层目录名与工作目录名往往不同，**在 handoff 第 3 节显式写明**，并说明“文中所有相对路径都相对于这个顶层目录” |
| 磁盘 / 依赖 / 权限 | 写明解压所需空间；PDF 渲染等“下游可选环节”明确标为“本次不做”；zip 内不放可执行文件 |

## 打包与校验

- `zipfile.ZipFile(..., allowZip64=True)`（>4 GB 必须）。
- **图片用 `ZIP_STORED`**（JPEG 重压无效、白耗时间），文本类用 `ZIP_DEFLATED, compresslevel=1`。
- 校验**不要**对大包用全量 `testzip()`（几十 GB 会白等很久）：改为**必备条目点名检查 + 随机抽 400 条读**（`z.read()` 时自动校验 CRC）。
- 报出：条目数、扩展名分布、原始体积→包体积、关键条目缺失清单。

## 顺序纪律（实际踩坑）

1. **交付目录内容定稿后再打包。** 打包中途改了交付目录里的文件 → zip 里就是旧版。
2. `zipfile` **不支持原地替换条目**，只能整个重写 → 改一次就得重打。所以：先冻结，再打包。
3. 大目录跨位置复制（如把十几 GB 清洗结果放进交付目录）**不要裸 `copytree` 一把梭**：复制可能被沙箱/权限**间断性拦截**（例如 Windows `WinError 5`），任务报 failed 但已经写了一部分。
   - 正确收口：**逐文件 size 比对 → 补齐 → 全量 SHA-256 复核**（多进程）。
   - 看到 `unresolved=0` 才算通过。

## 交付包典型结构

```
<交付根>/
├── 00_交接说明_HANDOFF.md     ← 写给接手 agent：决策表 / 调用规格 / 期望输出 / 改动边界 / 跨平台 / 风险 / 验收清单
├── 01_提示词/                 ← 最终版 + 改动对照
├── 02_样本/                   ← 样本清单.csv / 材料台账.csv / 材料说明.md / stimuli/{text,images}
├── 03_请求清单/requests.jsonl ← 机器直接消费
├── 04_上游数据/               ← 清洗阶段完整交付（只读引用）
├── 05_自检/                   ← 自检报告.md / 痕迹扫描.csv
└── 06_脚本/                   ← 生成脚本 + README（注明路径硬编码、仅供审计）
```

handoff 必须包含的“不可重新讨论”清单：模型 id 与参数（含 thinking 档位）、每请求样本数、图片上限、平台信息给不给、编号规则、评分口径有无改动。**接手方按它跑，不应再来问。**
